# Story 26.6 — Webhook : authentification entrante et routing multi-endpoints

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature
**Priorité** : Haute (l'authentification entrante est un prérequis d'exposition)
**Ordre d'implémentation** : **14 / 17** — phase F — Webhook
**Prérequis** : aucun
**Débloque** : Story 26.7

## Contexte

Les deux besoins partagent la même surface : la porte d'entrée du serveur webhook (`internal/modules/input/webhook.go`, `webhookInputConfig` dans `input-schema.json:90-130`).

### Volet 1 — Une seule forme d'authentification entrante

La configuration actuelle n'offre que `signature` (HMAC, `$defs/webhookSignature`) et `rateLimit`. Il n'y a **aucune authentification entrante** au sens classique :

- pas de `basic` — pourtant le mécanisme le plus courant côté émetteurs legacy
- pas de vérification de JWT (signature, `iss`, `aud`, `exp`)
- pas d'API key en header
- pas de mTLS

Un webhook cannectors exposé sans HMAC est donc un endpoint ouvert. Sur les connecteurs migrés dont l'émetteur ne sait pas signer, il n'existe aucune option.

### Volet 2 — Un seul chemin par port

`path` est une chaîne unique (`input-schema.json:95`) et `listenAddress` un port unique. Un connecteur qui reçoit trois types d'événements sur trois chemins doit lancer **trois process sur trois ports**. Les émetteurs, eux, publient généralement vers `…/webhook/orders`, `…/webhook/customers`, etc.

## Comportement attendu

### Authentification entrante

1. Bloc d'authentification entrante sur le webhook, avec au minimum : `basic`, `apiKey` (header configurable), `jwt` (validation de signature + claims + expiration), en complément de `signature` HMAC existante.
2. Réutiliser les briques existantes de `internal/auth` là où c'est pertinent, et **exclusivement des libs maintenues** pour JWT (pas de parsing de JWT maison — cf. `cannectors/CLAUDE.md`, réflexe « check library first »).
3. Échec d'authentification ⇒ `401`/`403` selon le cas, corps de réponse minimal, aucune fuite d'information, et log au niveau approprié sans révéler le secret présenté.
4. Combinaison possible de plusieurs mécanismes (ex. HMAC + IP allowlist) avec sémantique `all`/`any` explicite.
5. Comparaisons de secrets en temps constant (`crypto/subtle`).

### Routing multi-endpoints

6. Le webhook accepte plusieurs endpoints sur une même adresse d'écoute, chacun avec son `path`, sa méthode, son `dataField`, son authentification et éventuellement sa propre chaîne de traitement.
7. **Décision de conception à trancher** : un webhook multi-endpoints alimente-t-il un pipeline unique (avec un discriminant dans le record) ou plusieurs pipelines ? Recommandation : un input, plusieurs endpoints, et le discriminant d'endpoint injecté dans le record — le routage en aval est alors du ressort du filtre `condition` et de la Story 26.1. Cela évite de dupliquer un mécanisme de routage.
8. Chemin inconnu ⇒ `404` propre, comptabilisé.
9. Les limites existantes (`queueSize`, `maxConcurrent`, `requestTimeoutMs`) restent applicables ; leur portée (globale ou par endpoint) est documentée.

## Critères d'acceptation

- `AC1` — Webhook avec `basic` : requête sans en-tête → 401 ; mauvais mot de passe → 401 ; bon → 200 et record traité.
- `AC2` — Webhook avec `apiKey` en header : mêmes trois cas.
- `AC3` — Webhook avec `jwt` : signature invalide, `exp` dépassé, `aud` incorrect → rejetés séparément, chacun testé ; JWT valide accepté.
- `AC4` — HMAC `signature` existante inchangée (non-régression sur `webhook_test.go`).
- `AC5` — Combinaison de deux mécanismes en mode `all` puis `any` : comportement conforme.
- `AC6` — Aucun secret présenté ni attendu n'apparaît dans les logs, y compris en `--verbose`.
- `AC7` — Trois endpoints sur un seul port : chaque chemin reçoit et traite ses événements, l'identifiant d'endpoint est présent dans le record.
- `AC8` — Chemin non déclaré → 404, sans démarrage de traitement.
- `AC9` — Authentification distincte par endpoint respectée.
- `AC10` — Le contexte HTTP n'est pas propagé aux handlers différés (piège documenté dans `cannectors/CLAUDE.md`, corrigé en 22.7) : test de non-régression sur `queueSize` avec plusieurs endpoints.
- `AC11` — `cmd/cannectors/main.go` : le branchement `runWebhookPipeline` couvre le mode multi-endpoints.
- `AC12` — Exemple sous `examples/` : un webhook, trois chemins, auth basic, validé par `./cannectors validate --verbose`.
- `AC13` — `go test ./...` et `golangci-lint run ./...` passent.
