**Livré** : `httpclient.MergeQueryParams` (constructeur partagé), `urlEscape` corrigé en `%20`, câblage des 3 modules, deux chemins d'échec silencieux de l'output convertis en erreurs.

**Quatre défauts trouvés en revue et corrigés** :

- **`httpPolling` perdait toujours `queryParams` dès qu'une `pagination` était configurée.** `Fetch` fusionnait dans une variable locale, mais la branche paginée appelait `fetchWithPagination(ctx)`, qui reconstruisait son propre endpoint depuis `h.endpoint` brut. Le mode d'échec fondateur de la story survivait donc sur tout pipeline paginé — et le log `input fetch started`, qui affiche l'endpoint fusionné, le masquait. `fetchWithPagination` reçoit désormais l'endpoint résolu et ne le reconstruit plus (le `buildEndpointWithState` interne était de surcroît un doublon). Couvert par `TestHTTPPollingQueryParamsAreSentWithPagination` et `TestHTTPPollingStateParamsAreSentWithPagination`.
- **AC7 n'était pas tenu sur `httpRequest`** : `resolveEndpointForRecord` faisait un round-trip `url.Parse` / `q.Encode()` inconditionnel, donc un endpoint écrit `?b=2&a=1` partait en `?a=1&b=2` même sans `queryParams` ni `keys`. `http_call` et `httpPolling` respectaient déjà AC7 ; l'output était le seul à diverger. Le round-trip est maintenant sous garde (`len(QueryParams) > 0 || hasQueryKey()`), comme le `hasQuery` de `http_call`. Couvert par `TestResolveEndpointForRecordLeavesTheQueryStringAlone` et `TestResolveEndpointForRecordStillMergesIntoAnExistingQuery`.
- **La clé de cache par défaut de `http_call` ignorait l'URL réellement appelée** : elle était bâtie sur `m.endpoint` **brut** + les valeurs de `keys`. En rendant `queryParams` templatable, la story créait un nouveau vecteur de collision — deux records ne différant que par un `queryParams: {tenant: "{{ record.tenantId }}"}` partageaient un slot et le second recevait la réponse du premier. L'URL est désormais construite avant la consultation du cache et sert de clé par défaut (les valeurs de `keys` restent en suffixe : les clés `header` n'atteignent pas l'URL). Couvert par `TestHTTPCallQueryParamsTemplateSeparatesCacheEntries` et `TestHTTPCallCacheStillHitsOnIdenticalURLs`. Effet de bord voulu : la doc affirmait déjà « the resolved URL is the cache key », ce qui est maintenant vrai.
- **`TestHTTPPollingStateParamsWinOverQueryParams` ne testait pas ce que son nom annonçait** : aucun état n'était persisté, donc il vérifiait seulement la survie du défaut statique. Scindé en deux — ce cas-là garde son propre test (`…QueryParamsSurviveAnEmptyState`), et la précédence état > `queryParams`, affirmée dans le code comme dans la doc publiée, est enfin couverte avec un curseur réellement présent.

**Deux défauts trouvés en revue et corrigés** :

- `http_call` appliquait `queryParams` **avant** les remplacements de `{param}`. La fusion parse et ré-sérialise l'URL, ce qui percent-encode les accolades (`/orders/{id}` → `/orders/%7Bid%7D`) : le placeholder n'était plus jamais substitué et la requête partait avec `%7Bid%7D` dans son path. Les remplacements de path passent désormais en premier ; couvert par `TestHTTPCallPathKeySurvivesQueryParams` et `TestHTTPCallPathAndQueryKeysWithQueryParams`.
- `httpRequest` injectait ses valeurs de `queryParams` brutes : `{{ record.name }}` partait encodé littéralement. Même traitement que `http_call` (rendu `TargetText`, encodage unique par le sérialiseur) ; couvert par `TestResolveEndpointForRecordRendersQueryParamTemplates`.

**Deux tests corrigeaient le bug de leur côté** :
- `TestEngine_URLTarget` attendait `a+b%26c` — l'hypothèse « query uniquement ».
- `TestHTTPRequestModule_Templating_URLEncoding` acceptait `hello+world` dans le path **décodé**, ce qui ne pouvait passer que parce que l'encodage était faux. Réécrit pour asserter que l'espace survit au trajet.

## Contexte

Deux défauts distincts partagent la même cause racine : il n'existe **pas de constructeur d'URL partagé**. Chaque module HTTP reconstruit son endpoint à sa façon, et seul `httpRequest` (output) a une implémentation complète.

### Symptôme 1 — `queryParams` accepté mais ignoré

`queryParams` est déclaré dans `$defs/httpRequestBase` (`internal/config/schema/common-schema.json:189`), donc **hérité par `httpPolling`, `http_call` et `httpRequest`**. La struct partagée le porte également (`internal/moduleconfig/shared.go:16`).

Mais la seule lecture du champ se trouve dans l'output :

- `internal/modules/output/http_request_url.go:20` et `:85` — `h.request.QueryParams`

Aucune occurrence dans `internal/modules/input/http_polling*.go` ni `internal/modules/filter/http_call.go`.

Conséquence : un pipeline qui déclare `queryParams` sur `httpPolling` ou `http_call` **valide sans avertissement** et part en production avec des paramètres silencieusement perdus. C'est le pire mode d'échec possible : ni erreur de validation, ni log.

### Symptôme 2 — L'espace devient un `+` littéral dans un segment de path

> **Correction du 2026-08-16.** La rédaction initiale de cette story affirmait que les valeurs de gabarit étaient injectées **brutes** dans l'URL, avec pour exemple un paramètre `Fils` parasite. **C'est faux.** `template.TargetURL` injecte un échappement à la compilation (`internal/template/escape.go:47`, `escapeFilterFor`), et `http_call` comme `httpRequest` rendent bien leur endpoint avec ce target (`http_call.go:872`, `http_request_url.go:56`). Le vrai défaut est plus étroit — et différent.

`urlEscape` est `url.QueryEscape` pour **toutes** les positions d'URL (`internal/template/escape.go:95`) :

```go
func urlEscape(s string) string { return url.QueryEscape(s) }
```

Or `QueryEscape` encode l'espace en `+`. C'est correct dans une query string, où `+` est un alias historique de l'espace — et **faux dans un segment de path**, où `+` n'est qu'un caractère `+`.

Mesuré sur un serveur de test, avec `record.name = "Dupont & Fils"` :

| Position | Sur le fil | Décodé par le serveur | Verdict |
|---|---|---|---|
| `?name={{ record.name }}` | `?name=Dupont+%26+Fils` | `Dupont & Fils` | ✅ correct |
| `/orders/{{ record.name }}` | `/orders/Dupont+%26+Fils` | `Dupont+&+Fils` | ❌ espaces devenus `+` |

Le `&` est correctement échappé dans les deux cas. Seul l'espace en position de path est cassé — mais silencieusement : la requête part, le serveur répond, et c'est la donnée qui est fausse.

### Symptôme 3 — `httpPolling` ne rend aucun gabarit dans son endpoint

`buildRequest` (`internal/modules/input/http_polling_request.go:22`) reçoit l'endpoint déjà résolu et n'appelle jamais le moteur de gabarits. Il n'existe donc aucun point d'accroche pour un template dans l'URL d'un input HTTP — ce qui bloque aussi la Story 25.5.

## Comportement attendu

1. `queryParams` est honoré à l'identique sur `httpPolling`, `http_call` et `httpRequest`, y compris avec templates dans les valeurs.
2. Toute valeur injectée dans l'URL — segment de path issu d'un template, valeur de query param, valeur de `keys` — est percent-encodée selon son contexte (`url.PathEscape` pour le path, encodage query pour la query string).
3. La structure de l'URL écrite par l'auteur du pipeline n'est pas altérée : les `?`, `&`, `/` littéraux de l'endpoint restent structurels. Seules les **valeurs interpolées** sont encodées.
4. Un endpoint final non parsable est une **erreur**, pas un warning suivi d'un envoi.

## Approche retenue

### Symptôme 2 — encoder l'espace en `%20`, pas en `+`

Une seule fonction d'échappement suffit, à condition qu'elle soit correcte dans les deux positions. `%20` est valide **partout** : un décodeur de query string accepte `%20` aussi bien que `+`, et un décodeur de path n'accepte que `%20`. Il suffit donc de neutraliser le `+` produit par `QueryEscape` :

```go
func urlEscape(s string) string {
    return strings.ReplaceAll(url.QueryEscape(s), "+", "%20")
}
```

Le remplacement est sûr : un `+` littéral présent dans la donnée a déjà été encodé en `%2B` par `QueryEscape`, donc les seuls `+` restants dans la sortie sont ceux issus d'espaces.

Alternatives écartées :

- **Dédoubler le target** (`TargetURLPath` / `TargetURLQuery`) — un même endpoint contient les deux positions (`/orders/{{name}}?q={{term}}`), un target unique par gabarit ne peut pas les distinguer.
- **Rendre le moteur conscient de la position** en analysant le texte autour du placeholder — c'est du vrai échappement contextuel, mais une chirurgie du moteur pour un défaut qu'une fonction d'échappement correcte suffit à supprimer.
- **`url.PathEscape`** — n'échappe ni `&` ni `=` ni `?`, donc inutilisable pour une valeur de query.

### Symptôme 1 — constructeur d'URL partagé

Extraire dans `internal/httpclient` un constructeur consommé par les trois modules : endpoint rendu, `queryParams` (avec gabarits), `keys`. La fusion et la précédence sont alors définies une seule fois.

## Critères d'acceptation

- `AC1` — Un pipeline `httpPolling` avec `queryParams: {status: open}` émet une requête vers `...?status=open`.
- `AC2` — Idem pour `http_call`.
- `AC3` — Les valeurs de `queryParams` acceptent les templates (`{{record.id}}`) et sont encodées.
- `AC4` — `queryParams` déclaré à la fois dans l'endpoint (`?a=1`) et dans `queryParams` : la précédence est documentée et testée (comportement actuel de l'output : `q.Set` écrase).
- `AC5` — Une valeur de gabarit contenant `& # ? + = /`, un espace et un caractère UTF-8 produit une URL correctement décodée par le serveur, **en position de path comme de query**, vérifiée sur les 3 modules.
- `AC6` — Un endpoint final invalide après rendu retourne une erreur de module (respectant `onError`), sans requête émise.
- `AC7` — Tests de non-régression : les endpoints sans gabarit ni `queryParams` sont émis **inchangés** (pas de round-trip `url.Parse`/`String` qui normalise l'URL).
- `AC8` — `go test ./...` et `golangci-lint run ./...` passent.

## Hors portée
