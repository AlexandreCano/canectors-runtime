# Story 26.5 — OAuth2 : jeu complet de grant types + exploitation de la réponse du token

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature
**Priorité** : Haute (bloquant sec sur certaines migrations : sans le bon grant type, le connecteur ne s'authentifie pas)
**Ordre d'implémentation** : **11 / 17** — phase D — Authentification
**Prérequis** : Story 25.5
**Débloque** : Story 26.2

## Contexte

Deux besoins qui ne se séparent pas en pratique : ils apparaissent ensemble sur le même connecteur (typiquement Salesforce et assimilés).

### Volet 1 — Un seul grant type supporté

`credentialsOAuth2` (`internal/config/schema/auth-schema.json:119`) exige `tokenUrl`, `clientId`, `clientSecret` et propose `scope`. Il n'y a **aucun champ `grantType`** : le flux est implicitement et exclusivement `client_credentials` (`internal/auth/oauth2.go`).

Manquent notamment :

- `password` (Resource Owner Password Credentials) — explicitement demandé, encore massivement utilisé par les API legacy migrées
- `refresh_token` — indispensable pour les intégrations à token long
- `authorization_code` — nécessite un aller-retour interactif, à cadrer (voir plus bas)
- `jwt-bearer` / `assertion` (RFC 7523) — utilisé par les intégrations serveur-à-serveur Salesforce/Google

### Volet 2 — La réponse du token n'est pas exploitable

Certaines API renvoient dans la réponse du token des informations nécessaires pour construire les requêtes suivantes — l'exemple canonique étant `instance_url` chez Salesforce, ou un `api_domain`, un `tenant_id`, un `id`. Aujourd'hui la réponse est consommée pour en extraire l'`access_token` et le reste est perdu : impossible d'écrire un endpoint d'input basé sur l'URL d'instance retournée.

## Comportement attendu

### Grant types

1. Champ `grantType` explicite dans `credentialsOAuth2`, avec `client_credentials` par défaut (aucune rupture des pipelines existants).
2. Champs requis conditionnés au grant type via des blocs `if`/`then` dans le schéma : `password` exige `username`/`password`, `refresh_token` exige `refreshToken`, `jwt-bearer` exige la clé et les claims.
3. Rotation de refresh token gérée : si le serveur renvoie un nouveau `refresh_token`, il doit être persisté (sinon le connecteur se casse au run suivant). Interaction avec la persistance d'état — **point de conception à trancher** : où stocke-t-on un secret rotatif ?
4. Cache de token (`internal/auth/oauth2_tokencache.go`) : la clé de cache doit inclure le grant type et ses paramètres distinctifs, pour éviter toute réutilisation croisée (critique en multi-tenant, Story 26.2).
5. `authorization_code` : ne pas l'implémenter à moitié. Soit un mode « le refresh token est fourni en configuration, obtenu hors bande », soit une commande CLI dédiée d'obtention initiale. À cadrer explicitement — recommandation : couvrir `refresh_token` d'abord et documenter l'obtention hors bande.

### Réponse du token

6. Les champs de la réponse du token sont exposés dans un contexte de rendu (ex. `auth.instance_url`), utilisable partout où `state.*` l'est (Story 25.5) : `endpoint`, headers, `queryParams`, body.
7. Les valeurs sensibles (`access_token`, `refresh_token`) sont **exclues** de ce contexte ou explicitement marquées, et jamais loguées ni affichées en `--dry-run`.
8. Rafraîchissement : si le token est renouvelé en cours d'exécution et que `instance_url` change, les requêtes suivantes utilisent la nouvelle valeur.

## Critères d'acceptation

- `AC1` — Un pipeline OAuth2 existant sans `grantType` continue de fonctionner en `client_credentials`.
- `AC2` — `grantType: password` avec `username`/`password` obtient un token (test avec serveur de token stub).
- `AC3` — `grantType: refresh_token` obtient un token ; une rotation de refresh token renvoyée par le serveur est persistée et réutilisée au run suivant (test sur deux runs).
- `AC4` — `grantType: jwt-bearer` produit une assertion signée valide (signature vérifiée dans le test), via `crypto/*` ou `golang.org/x/crypto` — aucune implémentation cryptographique maison.
- `AC5` — Combinaisons de champs invalides rejetées par `cannectors validate` avec un message nommant le grant type et le champ manquant.
- `AC6` — Deux configurations OAuth2 différant uniquement par le grant type ne partagent pas d'entrée de cache de token.
- `AC7` — `{{ auth.instance_url }}` dans l'endpoint d'un `httpPolling` résout la valeur renvoyée par le serveur de token.
- `AC8` — `access_token` / `refresh_token` absents des logs à tous les niveaux, y compris `--verbose`, et absents de la sortie `--dry-run` (test d'assertion sur la sortie).
- `AC9` — Renouvellement en cours d'exécution avec changement d'`instance_url` : les requêtes suivantes ciblent la nouvelle URL.
- `AC10` — Exemple sous `examples/` d'un polling authentifié en `password` avec endpoint dérivé de la réponse du token, validé par `./cannectors validate --verbose`.
- `AC11` — `go test ./...` (`internal/auth` est partagé ⇒ portée large) et `golangci-lint run ./...` passent.
