# Story 26.2 — Exécution multi-tenant d'un même pipeline

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature (structurante)
**Priorité** : Haute (cas d'usage central pour un déploiement SaaS)
**Ordre d'implémentation** : **17 / 17** — phase G — Échelle
**Prérequis** : Story 25.5, Story 26.5, Story 26.4

## Contexte

Un même connecteur doit tourner pour N clients avec la même logique et des paramètres différents : URL d'instance, credentials, mapping de quelques champs, calendrier.

Aujourd'hui la seule voie est de **dupliquer le fichier YAML par tenant** et de jouer sur les variables d'environnement (`${VAR}`). Cela ne marche pas :

- l'état persistant est indexé par `pipelineID` — deux tenants sur le même fichier partageraient leur watermark, ou imposent N fichiers donc N IDs
- 50 tenants = 50 fichiers à maintenir synchronisés, sans mécanisme de factorisation (cf. Story 26.4 pour les gabarits)
- un seul process ne peut pas servir plusieurs tenants ; il faut N process, chacun avec son environnement

## Comportement attendu

1. Un pipeline peut déclarer une **dimension tenant** : une source de tenants (liste inline, fichier externe, requête SQL, variables d'environnement préfixées) et un jeu de paramètres par tenant.
2. Les paramètres du tenant sont disponibles dans un contexte de rendu dédié (ex. `tenant.*`), utilisable partout où `state.*` l'est (cf. Story 25.5) — même mécanisme, pas un second système.
3. **Isolation de l'état** : la clé d'état inclut le tenant. Le watermark du tenant A ne doit jamais être lu par le tenant B — c'est le point le plus critique de la story.
4. Isolation des credentials : l'authentification (y compris les caches de token OAuth2, `internal/auth/oauth2_tokencache.go`) est cloisonnée par tenant.
5. Politique d'exécution explicite : séquentielle ou concurrente avec une borne de parallélisme ; échec d'un tenant n'arrête pas les autres par défaut.
6. Observabilité : chaque log/erreur/métrique porte l'identifiant de tenant, et le rapport de fin d'exécution est par tenant.
7. `--dry-run` et `validate` fonctionnent sur un pipeline multi-tenant ; un flag permet de cibler un seul tenant (`--tenant <id>`) pour le debug.

## Critères d'acceptation

- `AC1` — Un pipeline mono-tenant existant reste inchangé (dimension tenant absente ⇒ exécution actuelle).
- `AC2` — Un pipeline à 3 tenants exécute 3 fois la logique avec les paramètres respectifs.
- `AC3` — Test d'isolation d'état : après une exécution, les 3 tenants ont 3 watermarks distincts persistés, et un run suivant reprend le bon pour chacun.
- `AC4` — Test d'isolation d'authentification : 3 tenants avec 3 credentials OAuth2 obtiennent 3 tokens distincts et le cache ne fuit pas entre tenants.
- `AC5` — L'échec du tenant 2 n'empêche pas les tenants 1 et 3 ; le code de sortie et le rapport reflètent l'échec partiel.
- `AC6` — Exécution concurrente bornée : le parallélisme configuré est respecté (test avec compteur d'appels simultanés).
- `AC7` — `--tenant <id>` n'exécute que ce tenant.
- `AC8` — Un exemple sous `examples/` multi-tenant, validé par `./cannectors validate --verbose`.
- `AC9` — `go test ./...` et `golangci-lint run ./...` passent.

## Risques / points de conception à trancher

- **Périmètre de la source de tenants** : commencer par une liste inline + fichier externe. Une source SQL/API de tenants est une extension ultérieure — sinon la story ne finit jamais.
- **Scheduling** : un CRON par tenant ou un CRON global ? Recommandation : global d'abord, per-tenant en extension.
- **Secrets** : référencer des credentials par tenant sans les écrire dans le YAML (cf. `operations/secrets`).

## Dépendances

- Story 25.5 (contexte de rendu unifié) — `tenant.*` doit réutiliser le même moteur.
- Story 26.4 (factorisation des gabarits) — utile mais non bloquant.
