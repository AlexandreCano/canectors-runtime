# Story 26.9 — Watermark d'état dérivé des données : `lastTimestamp = max(<champ>)`

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature
**Priorité** : Haute (correction de fond sur la fiabilité de l'incrémental)
**Ordre d'implémentation** : **09 / 17** — phase C — Incrémental
**Prérequis** : Story 26.10, Story 25.5, Story 26.8
**Débloque** : Story 26.11, Story 26.3

## Contexte

Le timestamp d'état est aujourd'hui l'**horloge de l'exécuteur**, pas une donnée du flux :

```go
// internal/runtime/pipeline.go:149
func (e *Executor) persistState(pipelineID string, executionStart time.Time, lastID *string, ...)
```

Le watermark persisté est donc dérivé de `executionStart`. Le schéma ne propose d'ailleurs qu'un `timestamp.enabled` + `timestamp.queryParam` (`common-schema.json:602-617`) : aucun champ pour désigner la colonne métier de référence. Seul l'input `database` offre une notion voisine avec `incremental` (`$defs/databaseIncrementalConfig`).

Trois failles concrètes :

1. **Décalage d'horloge** — si l'horloge du runtime diffère de celle du système source, des enregistrements sont perdus ou rejoués à chaque cycle.
2. **Latence de publication** — un enregistrement dont le `LastModifiedDate` est antérieur au `executionStart` mais qui devient visible après (transaction validée entre-temps) est manqué définitivement.
3. **Pagination longue** — sur une extraction de plusieurs minutes, `executionStart` ne dit rien de ce qui a réellement été lu.

Un watermark basé sur `max(LastModifiedDate)` des records effectivement traités règle les trois, parce qu'il ne s'appuie que sur ce qui a été vu.

## Comportement attendu

1. Configuration d'une stratégie de watermark explicite dans `statePersistence.timestamp` : `executionStart` (actuel, conservé) ou `maxField` avec le chemin du champ.
2. Le maximum est calculé sur les records **effectivement traités avec succès**. Décision à trancher : les records en `skip` comptent-ils ? Recommandation : **non** — un record ignoré n'est pas traité, l'inclure le rend irrécupérable. À rendre configurable si besoin, en lien avec la Story 26.10.
3. Parsing de la valeur du champ : formats acceptés explicites (RFC 3339 en premier), fuseau géré comme dans la Story 26.8, via stdlib.
4. Cas limites : aucun record (watermark inchangé, pas de régression en arrière), champ absent sur certains records (comportement configurable : ignorer / erreur), valeur non parsable (erreur respectant `onError`).
5. Le watermark ne recule **jamais** : garde explicite `nouveau >= ancien`.
6. Chevauchement configurable (*overlap* / *lookback*, ex. « moins 30 secondes ») pour absorber la latence de publication résiduelle — les doublons étant préférables aux pertes dans la plupart des migrations. À rendre optionnel et documenté comme tel.
7. Cohérence avec l'input `database` : la même stratégie doit être exprimable pour les 3 inputs, avec les mêmes noms de champs de configuration.

## Critères d'acceptation

- `AC1` — Stratégie `executionStart` : comportement actuel inchangé (non-régression).
- `AC2` — Stratégie `maxField` : après un run sur 3 records de timestamps différents, l'état persisté vaut le maximum des trois.
- `AC3` — Records reçus dans un ordre non trié : le maximum est correct.
- `AC4` — Un record en échec `skip` n'entre pas dans le calcul (comportement retenu, testé).
- `AC5` — Aucun record traité : le watermark n'est pas modifié.
- `AC6` — Un watermark calculé inférieur à l'existant n'est pas persisté (garde de monotonie testée).
- `AC7` — Champ absent / valeur non parsable : comportements configurés respectés, messages d'erreur nommant le champ et le record.
- `AC8` — Pagination sur 3 pages : le maximum couvre l'ensemble des pages.
- `AC9` — `overlap` de 30 s : le watermark persisté est bien le max moins l'overlap, et le run suivant relit la fenêtre attendue.
- `AC10` — La configuration est identique pour `httpPolling`, `soapPolling` et `database` (nommage aligné avec `databaseIncrementalConfig`).
- `AC11` — Test sur deux runs consécutifs : aucun record perdu, doublons bornés à la fenêtre d'overlap.
- `AC12` — `go test ./...` et `golangci-lint run ./...` passent.
