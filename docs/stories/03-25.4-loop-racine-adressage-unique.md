### Mesure avant correction

| Écrit dans un gabarit | Résolvait |
|---|---|
| `{{ record.line.number }}` | `L1` — élément courant, préfixé |
| `{{ record.record.orderId }}` | `ORD-1` — racine, double préfixe |
| `{{ record.orderId }}` | **vide, silencieusement** |

Le troisième cas est le plus coûteux : c'est ce que tout le monde écrit, et il ne produisait ni valeur ni erreur.

### Correctif

`template.ContextForRecord` détecte un scope de loop et le déplie : les alias deviennent des variables de premier niveau, `record` désigne le record racine. Un seul point de construction, partagé par **tous** les sites de rendu par record : `http_call`, `sql_call`, `httpRequest`, `database`, `soap_call`, `soaputil` (endpoint, headers, attachements) et `soapclient` (body et headers XML de l'enveloppe). Le seul site restant sur un contexte nu est l'input `database`, qui n'est jamais dans un scope.

Le body SOAP a été le piège de cette story : il est rendu à part, dans `soapclient.EvaluateXMLTemplate`, à partir du record brut. Oublié, il laissait `soap_call` coupé en deux — endpoint et `keys` en nouvelle convention, body en ancienne.

La détection exige **deux** signaux — `_metadata.loop` non vide **et** une clé `record` de type map — pour qu'un record ayant simplement un champ nommé `record` ne soit pas pris pour un scope. Testé.

Deux signaux ne suffisaient pas : rien n'empêchait une **source** de les fabriquer. Un payload portant `_metadata.loop` et un champ `record` était unwrappé comme un scope, et tous les gabarits en aval résolvaient `record.*` contre la fausse racine, sans erreur. `_metadata` est donc désormais retiré des records entrants par l'executor (`reserveMetadataField`, un seul point de passage : `executeInput`, que le pipeline soit pull ou push). Aucun input n'écrit ce champ — ce qu'on y trouve vient de la source. Régression couverte par `internal/runtime/metadata_reservation_test.go`, non vacuous : sans le retrait, `record.id` rend `"forged"`.

### Une troisième racine, celle qu'on oublie de nommer

Le scope n'est pas seulement l'endroit où vivent les alias : c'est aussi là qu'atterrit tout ce qu'un filtre imbriqué écrit **sans** le préfixe `record.` — le merge de réponse d'`http_call`, le `resultKey` de `sql_call`, une cible de `set` ou de `mapping`. Ces champs se relisent donc par leur **nom nu** (`{{ price }}`), dans un gabarit comme dans un field path, alors que hors loop c'est `record.price`.

C'est cohérent avec la convention retenue, mais indevinable si personne ne l'écrit : documenté dans la description du schéma, dans `loop/index.mdx` (section « Fields written at scope level ») et dans le tableau du contexte de `templating.mdx`. Corollaire assumé : un champ de scope nommé `record`, `meta`, `state` ou `pagination` est inatteignable en gabarit — contrairement à `itemName`, ça ne peut pas être rejeté au démarrage puisque ça dépend de la forme de la réponse.

### Anti-drift

La liste des alias réservés existe deux fois : en Go (`reservedItemNames`, qui assemble `template.ReservedVarNames()` et les clés de scope) et dans l'enum `not` du schéma, qui la rejoue pour que `validate` attrape l'erreur avant l'exécution. Un schéma plus permissif que le runtime transforme une erreur de validation en échec au démarrage. `TestLoopReservedItemNamesMatchTheSchema` lit le JSON et compare les deux ensembles ; le test en dur qui énumérait les six noms consomme maintenant `reservedItemNames()`.

### Effets de bord assumés

- **SOAP gagne `meta`** : `soaputil` et `soapclient` construisaient un contexte sans `Meta`, donc `{{ meta.* }}` échouait en strict dans un endpoint ou un body SOAP. Passer par `ContextForRecord` le peuple. La table de `templating.mdx` annonçait déjà « All templated fields » — elle est devenue vraie.
- **Coût du rendu** : le contexte est reconstruit à chaque champ rendu. `Extra` reçoit donc le scope **tel quel**, sans copie ni filtrage : `Vars` assigne les noms réservés en dernier, ce qui écrase la clé `record` du scope par la racine. `TestVarsReservedNamesWinOverExtra` n'est plus une ceinture-bretelle, il est porteur.

Ajout : `itemName` ne peut plus valoir `meta`, `state` ni `pagination`. L'alias devenant une variable de premier niveau, il masquerait la variable de contexte — et perdrait la collision au rendu, donc la loop ne marcherait tout simplement pas, sans rien dire. Rejeté à la construction du pipeline.

## Contexte

Le filtre `loop` construit un *scope record* (`buildLoopScope`, `internal/modules/filter/loop.go:307-336`) contenant :

- `record` → le record racine (`loopScopeRecord = "record"`, ligne 25)
- `<itemName>` → l'élément courant
- `_metadata.loop.<itemName>.index` → métadonnées

Le problème est que **deux conventions d'adressage cohabitent dans le même module** :

- Les gabarits (templates) résolvent depuis un contexte préfixé : on écrit `record.<alias>.champ`, et pour atteindre le record racine il faut `record.record.champ`.
- `keys[].field` adresse le scope directement : on écrit `<alias>.champ`, sans préfixe.

`record.record.number` n'est devinable par personne. Et la description du schéma décrit la mauvaise convention : `filter-schema.json:134` annonce *« The current item is exposed under the configured 'itemName' alias; the root record stays available as 'record' »* — vrai pour `keys[].field`, faux pour les gabarits.

## Comportement attendu

Une seule racine d'adressage dans le module, valable pour les gabarits **et** pour `keys[].field`.

Direction recommandée — **le scope est la racine** :

- `<alias>.champ` → l'élément courant
- `record.champ` → le record racine
- `_metadata.loop.<alias>.index` → métadonnées

Autrement dit : la convention déjà annoncée par le schéma, et déjà appliquée par `keys[].field`. C'est le rendu des gabarits qui est à corriger, pas la description ni `keys`.

Le projet n'étant pas en production (`cannectors/CLAUDE.md`), casser `record.record.*` est acceptable — et souhaitable.

## Critères d'acceptation

- `AC1` — Dans un `loop` avec `itemName: line`, un gabarit `{{ line.number }}` résout l'élément courant.
- `AC2` — Dans le même `loop`, `{{ record.orderId }}` résout le champ du record racine.
- `AC3` — `record.record.*` ne résout plus rien (ou lève une erreur explicite orientant vers `record.*`) — test dédié.
- `AC4` — `keys[].field` reste inchangé et cohérent avec les gabarits : `line.number` et `record.orderId` fonctionnent dans les deux mécanismes.
- `AC5` — Loops imbriqués : les alias des loops parents restent adressables sans préfixe (comportement de `buildLoopScope` pour `isNested`), documenté et testé sur 2 niveaux.
- `AC6` — `_metadata.loop.<alias>.index` accessible depuis un gabarit ; la garde `ErrLoopMetadataMutated` (ligne 262) reste active.
- `AC7` — La description de `loopFilterConfig` dans `filter-schema.json` décrit exactement le comportement implémenté, avec un exemple des deux racines.
- `AC8` — Un exemple sous `examples/` couvre loop + gabarit + `keys` sur les deux racines, validé par `./cannectors validate --verbose`.
- `AC9` — `go test ./...` (portée large : contrat de rendu partagé) et `golangci-lint run ./...` passent.
