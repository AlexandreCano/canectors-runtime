# Story 26.1 — Outputs multiples avec routage conditionnel

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature (structurante — modifie la topologie du pipeline)
**Priorité** : Haute
**Ordre d'implémentation** : **12 / 17** — phase E — Topologie
**Prérequis** : Story 26.10

## Contexte

Un pipeline cannectors est aujourd'hui strictement `input → filters[] → output` : **un** output singulier (`internal/runtime/pipeline.go` porte un `e.outputModule` unique, `pipeline-schema.json` déclare un objet `output`).

Les connecteurs migrés ont presque tous besoin de plus :

- envoyer le même record à deux destinations (système cible + journal d'audit)
- router selon le contenu (`type == "creation"` → POST, `type == "update"` → PUT, autre → base d'erreurs)
- déverser les rejets ailleurs que dans les logs (couplé à la Story 26.10, marqueur d'erreur)

Le filtre `condition` sait déjà router *à l'intérieur* de la chaîne de filtres (`then`/`else`, `filter-schema.json:102-125`), mais il ne peut pas choisir un output.

## Comportement attendu

1. `output` accepte soit un objet unique (compatible avec tout l'existant), soit une **liste d'outputs nommés**.
2. Chaque output porte une condition d'éligibilité optionnelle, exprimée avec la **même grammaire que le filtre `condition`** — pas un second langage d'expression.
3. Sémantique de diffusion explicite et configurable : `all` (chaque output éligible reçoit le record) vs `first-match` (routage exclusif). Ne pas deviner : les deux cas sont légitimes et l'auteur doit choisir.
4. Sémantique d'échec explicite : un output en échec fait-il échouer le record pour les autres ? `onError` par output, plus une politique globale.
5. `--dry-run` affiche l'aperçu **par output**, en indiquant quels records auraient été routés où (dépend de la Story 25.6 pour l'output database).
6. Les métriques/logs distinguent les outputs (compteurs par nom d'output).

## Critères d'acceptation

- `AC1` — Un pipeline avec un `output` objet unique fonctionne à l'identique (aucune régression sur les 40+ exemples).
- `AC2` — Un pipeline avec 2 outputs sans condition envoie chaque record aux deux.
- `AC3` — Un pipeline avec 3 outputs conditionnels en `first-match` route chaque record vers exactement un output, le dernier faisant office de défaut.
- `AC4` — Un record ne matchant aucune condition en `first-match` sans défaut : comportement documenté (drop explicite ou erreur), testé.
- `AC5` — Échec d'un output en mode `all` : politique `onError` respectée par output, sans empêcher les autres si configuré ainsi.
- `AC6` — `--dry-run` restitue le routage.
- `AC7` — Un exemple sous `examples/` avec routage création/modification/erreur, validé par `./cannectors validate --verbose`.
- `AC8` — `go test ./...` et `golangci-lint run ./...` passent.

## Dépendances / séquencement

- À implémenter **après** la Story 26.10 (marqueur d'erreur dans le record) : la principale motivation du multi-output est de router les rejets, ce qui suppose un statut exploitable dans le record.
- Interagit avec la Story 26.3 (agrégation en output) : une agrégation doit être définie par output, pas globalement.
