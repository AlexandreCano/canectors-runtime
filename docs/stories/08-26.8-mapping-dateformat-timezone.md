# Story 26.8 — `mapping` / transform `dateFormat` : option de fuseau horaire

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature (petite, à fort effet de bord fonctionnel)
**Priorité** : Moyenne-haute (les décalages de date sont des bugs silencieux et coûteux)
**Ordre d'implémentation** : **08 / 17** — phase C — Incrémental
**Prérequis** : aucun
**Débloque** : Story 26.9

## Contexte

Le transform `dateFormat` (`internal/modules/filter/mapping.go:472` → `applyDateFormat(value, config.Format)`) ne prend qu'un `format` (`filter-schema.json:455-458` : *« Date format pattern »*). Aucun fuseau horaire n'est configurable, ni en entrée ni en sortie.

Conséquences observées en migration :

- une date source sans fuseau (`2026-03-15T08:00:00`) est interprétée dans un fuseau implicite — impossible de dire lequel depuis le YAML
- une date source en UTC doit souvent être restituée en heure locale métier (ou l'inverse) : impossible
- au passage d'un changement d'heure, un décalage d'une heure apparaît sans qu'aucun log ne le signale
- deux exécutions du même pipeline sur deux machines avec des `TZ` différentes peuvent produire des résultats différents

## Comportement attendu

1. Deux options distinctes, car ce sont deux problèmes différents :
   - `inputTimezone` — fuseau supposé quand la valeur source **n'en porte pas**. Ignoré si la valeur porte un offset explicite.
   - `outputTimezone` — fuseau dans lequel la valeur est rendue.
2. Noms de fuseaux IANA (`Europe/Paris`), résolus via `time.LoadLocation` (stdlib) — pas de table d'offsets maison, pour que les changements d'heure soient corrects.
3. Le fuseau par défaut ne doit **pas** dépendre silencieusement du `TZ` de la machine. Décision à acter : soit UTC par défaut, soit une erreur de validation si la valeur source est ambiguë et qu'aucun `inputTimezone` n'est fourni. Recommandation : **UTC par défaut + documentation explicite** — un défaut prévisible bat un défaut « intelligent ».
4. Nom de fuseau inconnu ⇒ erreur de validation, pas un repli silencieux sur UTC.
5. Prévoir la disponibilité de la base de données de fuseaux dans les binaires distribués (voir `operations/cross-platform-builds`) : sur un système sans tzdata, `time.LoadLocation` échoue. Envisager l'import de `time/tzdata`.

## Critères d'acceptation

- `AC1` — Sans les nouvelles options, le comportement de `dateFormat` est strictement inchangé (non-régression sur `mapping_test.go`, `mapping_scenarios_test.go`).
- `AC2` — `inputTimezone: Europe/Paris` sur `2026-03-15T08:00:00` produit l'instant attendu (vérifié en UTC).
- `AC3` — Une valeur source portant un offset explicite ignore `inputTimezone` (test avec `+05:00`).
- `AC4` — `outputTimezone: Europe/Paris` rend une valeur UTC en heure de Paris.
- `AC5` — Test de changement d'heure : deux dates de part et d'autre de la transition mars/octobre produisent les offsets corrects (+01:00 / +02:00).
- `AC6` — Fuseau inconnu (`Europe/Atlantis`) rejeté par `cannectors validate` avec un message nommant l'option.
- `AC7` — Résultat identique quel que soit le `TZ` de l'environnement d'exécution (test avec deux valeurs de `TZ`).
- `AC8` — Les fuseaux fonctionnent sur un binaire distribué sans tzdata système (ou la limitation est documentée et détectée à l'exécution avec une erreur claire).
- `AC9` — Nouveaux tests écrits avec les helpers de fixtures existants (`mb()`, `tb()`, `assertMapped` — cf. `internal/modules/filter/mapping_fixtures_test.go`).
- `AC10` — `go test ./internal/modules/filter/...` puis `golangci-lint run ./...` passent.
