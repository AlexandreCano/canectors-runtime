**Fausse alerte levée en review** : brancher `Classifiable` dans `ClassifyError` ne change **aucune** décision de retry. Le seul `RetryExecutor` du runtime est celui de `httpclient.DoWithRetry`, et les erreurs qui y transitent sont déjà soit un `*ClassifiedError`, soit une erreur de transport brute — un `*SOAPFaultError`, un `*DatabaseError` ou une `*MappingError` n'y parviennent jamais (le fault SOAP est même parsé *après* la boucle HTTP). L'effet se limite aux libellés du rapport d'exécution (`ErrorCategory`, `ErrorType`), c'est-à-dire exactement AC0.

**`errorClassification` reste exposé sur `http_call` seul** : le `$def` vit dans `common-schema.json` mais n'est référencé que par `http_call`. `sql_call` n'a pas de code de statut protocole à surcharger, et personne n'a demandé le cas SOAP. La surface reste fermée tant qu'un besoin réel ne se présente pas.

**Précédence de classification assumée** : un `*ClassifiedError` déjà présent dans la chaîne prime sur `Classifiable`. C'est le verdict que le runtime a réellement appliqué, `retry.retryableStatusCodes` compris — le marqueur décrit ce qui s'est passé, pas ce que les règles par défaut auraient dit. La séparation annoncée entre `errorClassification` et le retry ne vaut donc que dans un sens ; la doc le dit désormais.

**Limite connue** : les marqueurs `sql_call` ne portent pas de `code` — `*database.DatabaseError` n'implémente pas `ModuleError`, et lui ajouter un `recordIndex` n'aurait pas de sens pour un type partagé entre input, filtre et output.

**Modules volontairement non annotés** — les outputs (`httpRequest`, `soapRequest`, `database`). Un output est terminal : `Send` ne renvoie qu'un compteur, il n'existe aucun canal pour remonter des marqueurs par enregistrement, et `skip`/`log` y sont déjà strictement identiques. Annoter y reviendrait à écrire dans des maps que personne ne lit. Leurs erreurs viennent de `httpclient` et sont donc déjà classifiées ; elles alimentent `ExecutionError`. **À reprendre en Story 26.1** (multi-output), où un enregistrement en échec aura enfin une destination.

**`script` non classifié** : `ScriptError` n'expose aucun code distinguant une interruption (timeout, annulation) d'une véritable erreur de données. Le classifier comme `validation` risquerait de figer en « fonctionnel » un échec purement technique. Laissé aux règles génériques.

**Dépendance ajoutée** : `mvdan.cc/xurls/v2` — extraction d'URLs dans du texte libre pour la rédaction des messages (AC6).

### Piège d'usage relevé

`expr` rejette `len(nil)`, et la clé réservée est **absente** d'un record qui n'a jamais échoué. L'idiome à documenter est donc `_errors != nil`, seul ou avant un `len()` :

```yaml
expression: "_errors != nil && len(_errors) > 0"
```

Injecter une liste vide dans l'environnement d'évaluation supprimerait le piège, mais le record **est** l'environnement passé à `expr.Run` (`condition.go:467`) : cela coûterait une copie de map par record et par filtre `condition`, sur tous les pipelines. Écarté.

## Contexte

`onError` n'accepte que trois valeurs (`common-schema.json:36-40` et `:57-61`, motif `^(?i)(fail|skip|log)$`), et aucune ne permet de traiter une erreur :

- **`fail`** arrête tout. Un seul enregistrement mal formé sur 10 000 bloque le lot entier.
- **`skip`** fait **disparaître l'enregistrement sans trace exploitable**. Il ne distingue pas un échec technique (timeout, 503 — à rejouer) d'un échec fonctionnel (400, validation métier — à ne jamais rejouer). Impossible de figer un `ERROR` définitif : le prochain cycle le reprendra et échouera de nouveau, indéfiniment.
- **`log`** laisse passer l'enregistrement mais **n'injecte aucun statut dans le record**. Le pipeline en aval ne peut pas savoir qu'un appel a échoué, donc ne peut ni router, ni acquitter sélectivement, ni écrire un rejet.

Le résultat, sur les connecteurs migrés : soit on accepte de tout perdre en silence, soit on accepte de boucler éternellement. Aucune des deux options n'est acceptable pour un connecteur de production.

Un simple **marqueur d'erreur dans l'enregistrement** (code HTTP, message, module fautif, classe d'erreur) débloque tout le reste : l'acquittement sélectif devient possible, `log` devient réellement utilisable, et le routage des rejets (Story 26.1) prend son sens.

## Comportement attendu

1. Quand un module échoue en mode `log`, il **annote le record** sous la clé réservée `_errors`, une **liste** (décision actée, cf. § Conception).
2. Contenu du marqueur :
   - `module` — type du module fautif
   - `category` — catégorie `errhandling.ErrorCategory` existante (`network`, `authentication`, `validation`, `rate_limit`, `server`, `not_found`, `unknown`)
   - `retryable` — booléen ; c'est **lui** qui porte la distinction technique / fonctionnel
   - `statusCode` — code HTTP (ou protocole) quand applicable, absent sinon
   - `code` — code d'erreur module (`ModuleError.ErrorCode()`) quand disponible
   - `message` — message assaini (URLs dépouillées de leurs secrets)
   - `attempts` — nombre de tentatives effectuées
   - `recordIndex` — position du record dans le lot remis au module
3. Le marqueur est adressable par le filtre `condition` et par les gabarits : `_errors[0].statusCode`, `_errors[0].retryable`.
4. **Pas de nouvelle taxonomie** : `category` + `retryable` proviennent de `ClassifiedError`, qui encode déjà la règle « 5xx / timeout / connexion / 429 ⇒ retryable ; 4xx hors 429 ⇒ non retryable » (cf. § Conception).
5. Le marqueur est **réservé et protégé** : un module ne doit pas pouvoir l'écraser accidentellement, comme `_metadata` l'est déjà dans `loop` (`ErrLoopMetadataMutated`, `internal/modules/filter/loop.go:262`).
6. Un compteur d'échecs par catégorie apparaît dans le rapport de fin d'exécution.
7. `skip` reste disponible mais sa sémantique de perte silencieuse est documentée comme telle, avec renvoi vers `log`.

## Conception (arrêtée avant implémentation)

### Décisions actées

| Question ouverte | Décision | Raison |
|---|---|---|
| `_error` unique ou `_errors[]` ? | **`_errors`, une liste** | Un record traverse plusieurs filtres d'appel ; un champ scalaire écraserait le premier échec, qui est souvent la cause racine |
| Nouveau mode `mark` ou enrichir `log` ? | **Enrichir `log`, pas de 4ᵉ mode** | `log` appende déjà le record d'origine et continue (`http_call.go:352-360`) : il ne lui manque que le marqueur. Ajouter `mark` laisserait `log` inutile et créerait deux modes quasi identiques |
| Taxonomie `technical` / `functional` ? | **Abandonnée** au profit de `category` + `retryable` | Voir ci-dessous |

### La taxonomie demandée existe déjà — et en mieux

`internal/errhandling/errors.go` implémente déjà l'intégralité de la classification que la story demandait de créer :

- `ErrorCategory` : `network`, `authentication`, `validation`, `rate_limit`, `server`, `not_found`, `unknown`
- `ClassifiedError{Category, Retryable, StatusCode, Message, OriginalErr}`
- `ClassifyHTTPStatus` applique **exactement** la règle par défaut décrite au point 4 : 401/403 → authentication non-retryable, 400/422 → validation non-retryable, 404 → not_found non-retryable, 429 → rate_limit retryable, 5xx → server retryable
- `ClassifyError`, `IsRetryable`, `IsFatal`, `GetErrorCategory`

Introduire un axe `class: technical | functional` en parallèle donnerait au runtime **deux réponses à la même question**, avec un risque de divergence — précisément le défaut que corrige la Story 25.4. `retryable` *est* l'axe technique/fonctionnel, et `category` le raffine.

### Prérequis découvert : les erreurs de module ne sont pas classifiées

`HTTPCallError` (`internal/modules/filter/http_call.go:104-113`) porte un champ `StatusCode`, implémente `ModuleError`, mais :

- n'encapsule aucun `*ClassifiedError`
- n'expose pas d'`Unwrap()`

Donc `errhandling.ClassifyError(httpCallErr)` ne trouve rien via `errors.As(err, &classified)`, n'est ni une erreur `net`/`url`/`context`, et **retombe sur le cas par défaut** : `CategoryUnknown`, `Retryable: true`, `StatusCode: 0`.

**Conséquence** : aujourd'hui un `http_call` qui échoue en 400 est classifié `unknown` / `retryable`. C'est l'inverse de ce que demandent AC1, AC2 et AC3. Le marqueur, branché tel quel, rapporterait `category: unknown, retryable: true, statusCode: 0` pour **toutes** les erreurs `http_call`.

Ce n'est pas propre à la story : `buildExecutionError` (`internal/runtime/pipeline.go:664-670`) alimente `ExecutionError.ErrorCategory` / `ErrorType` par le même chemin. Le rapport d'exécution annonce donc déjà `errorCategory: unknown` / `errorType: retryable` pour chaque échec de module typé.

**Correction retenue** — une interface d'auto-classification optionnelle dans `errhandling` :

```go
// Classifiable is implemented by module error types that know their own
// classification (typically because they carry a protocol status code).
type Classifiable interface {
    Classify() *ClassifiedError
}
```

`ClassifyError` la consulte via `errors.As` **avant** de retomber sur `CategoryUnknown`. `HTTPCallError` (et ses équivalents SOAP/SQL) l'implémente en déléguant à `ClassifyHTTPStatus(e.StatusCode, e.Message)` quand `StatusCode != 0`.

Alternatives écartées :

- **Ajouter `StatusCode()` à `ModuleError`** — casse tous les implémenteurs pour un besoin qui ne concerne que ceux qui ont un code protocole.
- **Détourner `Unwrap()`** pour renvoyer un `ClassifiedError` synthétique — fausserait `errors.Is` sur la cause réelle.
- **Lire `ErrorDetails()["status_code"]`** — archéologie dans une map non typée, fragile.

### Assainissement du message (AC6)

`urlsan.Sanitize` (`internal/urlsan/urlsan.go`) prend **une URL**, pas du texte libre. Or les messages de module interpolent des erreurs arbitraires et `HTTPCallError.ErrorDetails()` expose `endpoint` brut — un endpoint qui peut porter `?apikey=…` via `queryParams` ou un gabarit.

Il faut donc ajouter à `urlsan` une fonction de rédaction sur texte libre, qui repère les URLs incluses dans un message et applique `Sanitize` à chacune. `urlsan` est le bon propriétaire : c'est déjà le paquet feuille dédié à cette préoccupation, précisément pour éviter la duplication entre `httpclient` et `errhandling`.

### Factorisation

Le `switch m.onError { fail / skip / log }` est **recopié dans chaque module** (`http_call.go:334-361` et ses homologues). Le marqueur doit être construit et attaché par un helper partagé d'`errhandling`, pas par N copies de la même logique dans N modules — sinon la structure du marqueur divergera module par module, exactement comme `resultKey` a divergé (Story 25.2).

### Portée de l'implémentation

1. `internal/urlsan` — rédaction sur texte libre
2. `internal/errhandling` — `Classifiable`, branchement dans `ClassifyError`, type `Marker`, constructeur, helper d'annotation, helper de décision `onError`
3. Types d'erreur des modules — implémenter `Classifiable` (http_call, soap_call, sql_call, http_request, soap_request, database)
4. Modules — remplacer le `switch onError` local par le helper partagé
5. `internal/runtime` — compteurs par catégorie dans le rapport d'exécution
6. `set` / `mapping` — refus d'écriture sur la clé réservée (AC7)
7. Schéma + doc + exemple

## Critères d'acceptation

- `AC0` — `errhandling.ClassifyError` sur une erreur de module portant un code protocole retourne la catégorie correspondante, et non `CategoryUnknown` (prérequis, cf. § Conception ; corrige aussi `ExecutionError.ErrorCategory`).
- `AC1` — `http_call` échouant en 400 en mode `log` : le record continue et porte `_errors[0]` avec `category: validation`, `retryable: false`, `statusCode: 400`.
- `AC2` — Même appel en 503 : `category: server`, `retryable: true`, `attempts` renseigné après épuisement du retry.
- `AC3` — Timeout de connexion : `category: network`, `retryable: true`, sans `statusCode`.
- `AC4` — Un filtre `condition` sur `_errors[0].retryable == false` route correctement le record.
- `AC5` — Deux échecs successifs sur deux filtres différents : les deux marqueurs sont présents et ordonnés.
- `AC6` — Aucun secret (credential, token, URL avec credentials) dans `message` — test d'assertion.
- `AC7` — Une tentative d'écriture manuelle du champ réservé (via `set` ou `mapping`) est rejetée ou détectée.
- `AC8` — `fail` et `skip` conservent leur comportement actuel (non-régression).
- `AC9` — Le rapport de fin d'exécution compte les échecs par classe.
- `AC10` — Classification surchargée au niveau module : un 404 déclaré comme fonctionnel-acceptable est traité comme tel.
- `AC11` — Exemple sous `examples/` : appel enrichissant, marquage d'erreur, routage des rejets, validé par `./cannectors validate --verbose`.
- `AC12` — `go test ./...` (touche `internal/errhandling`, partagé ⇒ portée large) et `golangci-lint run ./...` passent.

## Débloque

- **Story 26.1** — le multi-output n'a d'intérêt plein qu'avec un statut d'erreur routable.
- **Story 26.9** — définit quels records comptent dans le watermark.
- **Story 26.7** — la réponse d'un webhook synchrone peut refléter le statut réel.
- **Story 26.3** — détermine si un membre en erreur fait échouer tout un groupe agrégé.

C'est la raison pour laquelle cette story est en **position 1** : elle est de périmètre modeste et conditionne le sens de quatre autres.
