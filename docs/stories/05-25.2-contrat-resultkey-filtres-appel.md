# Story 25.2 — Contrat unifié `resultKey` / `mergeStrategy` pour les filtres d'appel

**Epic** : 25 — Bugs remontés par les migrations de connecteurs
**Type** : Bug (incohérence de contrat)
**Priorité** : Haute
**Ordre d'implémentation** : **05 / 17** — phase B — Contrats
**Prérequis** : aucun
**Débloque** : Story 25.3

## Contexte

Les trois filtres d'appel (`http_call`, `soap_call`, `sql_call`) font conceptuellement la même chose : émettre un appel par record et fusionner la réponse dans le record. Mais leur contrat de fusion diverge :

| Filtre | `resultKey` | `mergeStrategy: append` |
|---|---|---|
| `soap_call` | accepté (`internal/modules/filter/soap_call.go`) | `resultKey` rendu **obligatoire** par le schéma (`filter-schema.json:311-314`) |
| `sql_call` | accepté (`internal/modules/filter/sql_call.go`) | `resultKey` rendu **obligatoire** par le schéma (`filter-schema.json:326-329`) |
| `http_call` | **refusé** — la clé de destination est hardcodée à `_response` | `append` sans destination configurable |

Le verbe `append` a donc deux significations selon le module, et un auteur de pipeline ne peut pas généraliser ce qu'il a appris de `soap_call` à `http_call`. Lors d'une migration où les trois filtres cohabitent, c'est une source d'erreur permanente.

Note complémentaire (cf. `cannectors/CLAUDE.md`) : `http_call` utilise **toujours** un cache LRU, et sans `keys` ni `cache.key` explicite tous les records partagent le même slot. Combiné à l'absence de `resultKey`, le module est le moins prévisible des trois.

## Décision actée

**Option A — aligner sur `soap_call`/`sql_call`.**

`http_call` accepte `resultKey`, avec `_response` comme valeur par défaut pour rester lisible, et `resultKey` obligatoire dès `mergeStrategy: append`.

L'alternative écartée (option B : convention de nommage implicite pour les trois, `resultKey` optionnel partout) l'a été parce que l'explicite bat l'implicite dans un fichier de configuration relu par un humain six mois plus tard. Le projet n'étant pas en production (`cannectors/CLAUDE.md`), le changement de contrat sur `http_call` est assumé — pas de shim, pas d'alias de compatibilité.

## Comportement attendu

1. `http_call` accepte `resultKey` avec la même sémantique que `soap_call` et `sql_call`.
2. Les blocs `if`/`then` du schéma sont factorisés en une définition partagée (`$defs/callFilterMergeConstraints`) référencée par les trois filtres — au lieu de deux blocs dupliqués et d'un module absent.
3. `mergeStrategy` accepte le même jeu de valeurs pour les trois modules, avec une sémantique documentée identique.
4. La valeur par défaut de `resultKey` pour `http_call` reste `_response` (pas de rupture inutile des exemples existants) mais devient surchargeable.

## Critères d'acceptation

- `AC1` — `http_call` avec `resultKey: enrichment` écrit la réponse sous `record.enrichment`.
- `AC2` — `http_call` sans `resultKey` continue d'écrire sous `_response`.
- `AC3` — `http_call` avec `mergeStrategy: append` sans `resultKey` échoue à la **validation** (`cannectors validate`), avec un message nommant le champ manquant.
- `AC4` — Les contraintes `append` ⇒ `resultKey` sont exprimées une seule fois dans `filter-schema.json` et partagées par les 3 filtres.
- `AC5` — Un pipeline d'exemple sous `examples/` démontre les 3 filtres avec un contrat de fusion identique, et passe `./cannectors validate --verbose`.
- `AC6` — Tableau comparatif des 3 filtres (stratégies × destination) dans la doc.
- `AC7` — `go test ./...` et `golangci-lint run ./...` passent.
