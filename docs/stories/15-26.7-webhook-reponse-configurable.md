# Story 26.7 — Webhook : réponse HTTP configurable

**Epic** : 26 — Fonctionnalités identifiées par les migrations de connecteurs
**Type** : Feature
**Priorité** : Moyenne-haute
**Ordre d'implémentation** : **15 / 17** — phase F — Webhook
**Prérequis** : Story 26.10, Story 26.6

## Contexte

`webhookInputConfig` (`input-schema.json:90-130`) ne décrit aucune réponse : code, en-têtes et corps renvoyés à l'émetteur sont figés dans le code (`internal/modules/input/webhook.go`).

Or l'émetteur d'un webhook interprète la réponse :

- certains exigent un corps précis (écho d'un jeton de vérification, `{"status":"ok"}`, un identifiant de corrélation)
- certains distinguent `200` et `202`, ou rejouent sur un code inattendu
- l'enregistrement d'un webhook chez un fournisseur passe souvent par un **challenge de vérification** : renvoyer la valeur reçue. Sans réponse configurable, l'enregistrement est impossible et la migration est bloquée avant même le premier événement.

Question de conception centrale : la réponse peut-elle dépendre du **résultat du traitement** ? Aujourd'hui `queueSize` permet un traitement asynchrone : la réponse est écrite avant que le pipeline n'ait tourné (et le contexte HTTP est annulé dès l'écriture — piège documenté dans `cannectors/CLAUDE.md`). Il faut donc deux modes clairement séparés.

## Comportement attendu

1. Bloc `response` configurable : `statusCode`, `headers`, `body` (avec gabarits).
2. **Deux modes explicites** :
   - *ack immédiat* (comportement actuel, asynchrone) : la réponse est statique ou dérivée de la **requête** uniquement. Aucun accès au résultat du pipeline.
   - *synchrone* : la réponse est produite après exécution du pipeline pour cet événement, et peut dépendre du résultat (succès/échec, données de sortie). Nécessite un timeout borné et un code de repli au dépassement.
3. Les gabarits de réponse ont accès au contexte de la requête (corps reçu, en-têtes, chemin) et, en mode synchrone, au résultat du traitement.
4. L'échappement contextuel s'applique au corps de réponse selon son content-type (`internal/template` — cible adaptée, pas d'injection).
5. Réponse d'erreur configurable séparément (échec d'authentification, corps invalide, échec de traitement) — sans divulguer d'informations internes par défaut.
6. Le mode synchrone doit rester compatible avec `maxConcurrent` et `requestTimeoutMs`, et ne pas propager un contexte annulé au pipeline.

## Critères d'acceptation

- `AC1` — Sans bloc `response`, le comportement actuel est strictement conservé (non-régression `webhook_test.go`).
- `AC2` — `response.statusCode: 202` renvoie bien 202.
- `AC3` — En-têtes de réponse personnalisés présents dans la réponse.
- `AC4` — Corps de réponse avec gabarit renvoyant une valeur du corps reçu (cas du challenge de vérification) : test de bout en bout.
- `AC5` — Mode synchrone : le corps de réponse contient une donnée produite par le pipeline.
- `AC6` — Mode synchrone en dépassement de timeout : code de repli renvoyé, pas de requête pendante, pas de goroutine fuitée (test avec pipeline lent).
- `AC7` — Mode synchrone avec échec de pipeline : réponse d'erreur configurée renvoyée, `onError` respecté.
- `AC8` — Un gabarit de réponse ne peut pas injecter de contenu non échappé (test avec une valeur reçue contenant des métacaractères du content-type).
- `AC9` — Aucun détail interne (stack, chemin de fichier, secret) dans les réponses d'erreur par défaut.
- `AC10` — En mode asynchrone, le contexte transmis au pipeline n'est pas celui de la requête (non-régression du bug corrigé en 22.7).
- `AC11` — Exemple sous `examples/` avec réponse de challenge, validé par `./cannectors validate --verbose`.
- `AC12` — `go test ./...` et `golangci-lint run ./...` passent.
