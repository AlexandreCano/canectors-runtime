# Story 25.3 — `http_call` : `dataField` pointant sur un tableau de plus d'un élément

**Epic** : 25 — Bugs remontés par les migrations de connecteurs
**Type** : Bug
**Priorité** : Haute (perte de données silencieuse)
**Ordre d'implémentation** : **06 / 17** — phase B — Contrats
**Prérequis** : Story 25.2

## Contexte

`extractDataField` (`internal/modules/filter/http_call.go:740-767`) traite trois cas :

```go
if dataMap, ok := data.(map[string]any); ok { return dataMap }            // objet → OK
if dataArr, ok := data.([]any); ok && len(dataArr) == 1 { ... }           // tableau de 1 → OK
logger.Warn("http_call dataField not found or invalid", ...)              // tout le reste
return make(map[string]any)
```

Un tableau de **0 ou ≥ 2 éléments** retombe donc dans le cas d'échec et retourne une **map vide**, avec un warning dont le message (`dataField not found or invalid`) est trompeur : le champ a bien été trouvé, il contient simplement plusieurs éléments.

Le record poursuit son chemin dans le pipeline avec un résultat vide, sans erreur, sans respecter `onError`. Sur une migration où l'API de référence renvoie systématiquement une liste (cas très courant : `{"results": [...]}`), le connecteur produit du vide en silence.

Note : le tableau de 0 élément est un cas fonctionnel légitime (« aucun résultat ») et doit être distingué de l'erreur.

## Décision actée

**Option 1 seule — conserver le tableau tel quel** sous `resultKey` (cf. Story 25.2), le pipeline itérant ensuite avec le filtre `loop`.

`onMultiple: first | last | all | error` (option 2) est écarté : `loop` couvre déjà l'itération, et réduire un tableau à un élément se fait explicitement avec un filtre `script`. Le champ pourra être ajouté si un besoin réel apparaît — il n'y a pas de coût de migration à l'ajouter plus tard.

Conséquence : un `dataField` sur tableau exige `mergeStrategy: append` ; `merge` et `replace` n'ont aucune destination capable d'accueillir une liste et remontent une erreur nommant la sortie (au runtime, puisque la forme de la réponse n'est pas connue à la validation).

**AC6 — alignement de `soap_call` retenu** plutôt que la simple documentation de l'écart : `soaputil.ValueAsRecordMap` enrobait un tableau multi-éléments sous une clé implicite `items` et un scalaire sous `value`, clés qu'aucun YAML ne nommait. Fonction supprimée ; `soap_call` passe la valeur brute au contrat de fusion partagé. `soap_polling` (`ValueAsRecords`) est inchangé : un input produit N records, ce qui est une sémantique légitimement différente.

Dans tous les cas :

- 0 élément ⇒ résultat vide **explicite** (tableau vide ou absence de clé, documenté), pas un warning « invalid ».
- Type réellement inattendu (scalaire, `null`) ⇒ erreur respectant `onError`, pas une map vide silencieuse.

**Précisions issues de la review** :

- **Tableau vide et `merge`/`replace`** : c'est un no-op (record inchangé), pas une erreur de forme. « Aucun résultat » est une réponse fonctionnelle que l'auteur du pipeline ne contrôle pas — seul un tableau **non vide** sans destination remonte une erreur. AC3 est donc tenu quelle que soit la stratégie.
- **Propriété de la réponse** : la valeur fusionnée dans le record est clonée (`cloneCallData`). Avec `cache.enabled` l'objet renvoyé par le LRU est partagé entre tous les records d'une même clé, et le pattern `append` + `loop` mute les items en place : sans clone, un record réécrivait les items d'un autre et empoisonnait l'entrée de cache. Verrouillé par `TestHTTPCall_CachedListIsNotSharedBetweenRecords`, `TestMergeCallMap_ClonesResponse` et le scénario test-lab (`match.owner` = `record.line_id`, SKU-001 partagé par L-1 et L-3).
- **Erreurs routables** : le contrat partagé expose `ErrCallResultType` et `ErrCallMergeStrategyMismatch`, classées `validation` non-retryable. `soap_call`, qui n'a pas de type d'erreur propre, devient ainsi aussi exploitable que `http_call` (qui garde en plus ses codes `HTTP_CALL_DATA_FIELD_*` / `HTTP_CALL_MERGE_MISMATCH`).

## Critères d'acceptation

- `AC1` — `dataField` sur un tableau de 3 objets : les 3 éléments sont accessibles dans le record en aval.
- `AC2` — Le résultat est directement consommable par le filtre `loop` (test d'intégration `http_call` → `loop`).
- `AC3` — `dataField` sur un tableau vide : pas de warning « invalid », résultat vide documenté, le record continue.
- `AC4` — `dataField` sur un scalaire ou absent : erreur qui traverse `onError` (`fail`/`skip`/`log`), plus de map vide silencieuse.
- `AC5` — Les messages de log distinguent les trois cas : champ absent, type inattendu, tableau multi-éléments.
- `AC6` — Alignement vérifié avec `soap_polling`/`soap_call` (`internal/modules/soaputil/soaputil.go`) : documenter tout écart restant de sémantique `dataField`.
- `AC7` — `go test ./...` et `golangci-lint run ./...` passent.
